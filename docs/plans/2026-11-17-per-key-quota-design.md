## §0 现状与缺口（事实核对，main 2d77ee43）

今天路由器对额度的了解全部来自**事后观测**，没有**本地计数**：

| 现有机制 | 文件 | 作用 | 盲区 |
|---|---|---|---|
| 响应头归一化 | `quota.py` `parse_quota_headers` | 把上游限流头（ratelimit-limit/remaining/reset、retry-after）解析成 `QuotaObservation`（requests/tokens 两维 + retry_at + 分类） | 只有上游回了头才有数；多数免费档不回 remaining |
| 失败后冷却 | `resilience.py` `ResilienceManager` | 按（提供方，模型，凭证槽）记 state/cooldown_until/quota；429/402 后按 `quota_cooldown_scale=8.0` 拉长冷却；`can_attempt` 守门 | 事后反应：必须先撞一次 429 才知道没额度 |
| 成本维 | `costing.py` `cost_factor` | 用实时 `quota_ratio`（剩余/上限）算成本分，低于 0.10 阈值降权不截断；无数据记 `missing_default=0.5` 不惩罚 | 无信号时等于盲选 |
| 排除 | `routing.py` `RoutePlanner.plan` | 全部凭证槽被 resilience 拦住的候选先剔除（`excluded_by_cost`），再按质量 0.5 / 成本 0.3 / 延迟 0.2 三维打分 | 剔除依据是"已知的坏"，不是"快用完的" |
| 展示 | `quota_view.py` | 只读展示：sufficient/tight/exhausted/stale/unknown 五档；明确"上游不报 used，绝不编造减法" | 只能展示观测到的，不能展示本地花掉的 |
| 文档档位 | `docs/provider-profiles.json` `free_tier` | 10 家提供方的免费档位说明；多数数值字段为 null，confidence 标 estimated/documented，"留空不编造" | 不是运行时真相源 |

缺口有三条，都是本 PRD 要补的：

1. **没有本地计数**。路由器不知道自己在窗口内已经发了多少请求、花了多少 token。`free_tier` 数值字段多为 null，`QuotaObservation` 依赖上游回头——两者都没有时，成本维只能给 0.5 默认分，等于没有额度概念。
2. **并行请求集体越线**。N 个并行请求读到的都是同一份上次响应头的 remaining 快照，全部通过守门，然后一起撞上 429。今天没有任何"进行中也算数"的机制。
3. **共享池不可见**。OpenRouter `:free` 路由是多模型共用一个池；按模型看 remaining 都够，池子其实已经空了。今天的键是（提供方，模型，凭证槽），没有池这一层。

## §1 目标与非目标

目标：让路由器按（平台、模型、密钥）真实计量剩余额度，并行请求也不越线；共享池按池计量。

非目标（写死，不在本 PRD 做）：

- 不改 BYOS 接入层（密钥注册、订阅状态、`prefer_subscribed` 排序归 PRD-173）。
- 不做额度预测（forecast）。只做计量与守门：数已经花掉的，拦马上要超的；不预测"按这个速度几小时后花完"。
- 不改三维权重体系（质量 0.5 / 成本 0.3 / 延迟 0.2 不动）。
- 不碰 `quota.py` 的解析逻辑（PRD-469 的事）、不碰冷却阶梯（PRD-468 的事）、不做 UI（PRD-201 的事）。

## §2 四维滑动窗口

### 2.1 四维定义

| 维 | 窗口 | 桶 | 量的含义 |
|---|---|---|---|
| RPM | 滚动 60 秒 | 1 秒 × 60 | 窗口内已派发的请求数 |
| RPD | 滚动 24 小时 | 1 小时 × 24 | 窗口内已派发的请求数 |
| TPM | 滚动 60 秒 | 1 秒 × 60 | 窗口内已用 token 估算 |
| TPD | 滚动 24 小时 | 1 小时 × 24 | 窗口内已用 token 估算 |

窗口一律是**滚动**窗口，不是自然日/自然分钟。原因：自然日边界涉及时区与"今天"的定义，是经典的边界 bug 来源；滚动窗口只依赖单调时间戳，行为处处一致。RPD 的"一天"就是过去 24 小时。

实现形态照抄 `latency.py` 的滑动窗口先例（PRD-059/T3 已验证的模式）：每维一个桶数组，时间推进时丢弃过期桶；计数是 O（桶数）求和。

### 2.2 键格式

窗口键（count key）：

```
{platform}:{upstream_model_id}:slot-{n}:{window}
```

- `platform`：注册表里的提供方名；`upstream_model_id`：上游模型 id（与 `ResilienceManager` 的键口径一致）。
- `slot-{n}`：凭证槽序号，照 `costing.credential_slots` 的编号（无鉴权提供方为 slot-0）。**键里只放槽序号，永不放密钥原文**——与 `failover_decisions` 脱敏、`audit.py` 只记 sha256 同一条隐私线。
- `window` ∈ {rpm, rpd, tpm, tpd}。

池键（§5）：`pool:{pool_id}:{window}`。

### 2.3 上限来源（优先级，写死）

守门需要"上限"和"已用"两边都有证据。**上限只认三档来源，按优先级取**，三档都没有时窗口只计数、不守门：

1. **上游响应头观测值**（`QuotaObservation.limit`）：最新鲜的证据。超过 `QUOTA_SIGNAL_MAX_AGE_SECONDS`（30 分钟，PRD-096/T1 §2 已定）即视为过期，降级到下一档。
2. **已核实的文档值**：`provider-profiles.json` `free_tier` 里 `confidence=documented` 的数值。`confidence=estimated` 的值和 null 字段**永远不能当上限**——这是 202/T1 定下的诚实线（"禁止脑补 null 字段"），本 PRD 沿用。
3. **签名目录值**（PRD-466 落地后）：目录里的 rpm/rpd/tpm/tpd。若 466 未落地，本档不存在，跳过。目录值新于静态文档时优先于第 2 档；沿用 466 的版本底线规则。

三档都没有：**窗口只计数、不守门**。计数本身就是价值（给以后学上限、给 201 看板、给 229 学习网关留数据），但绝不能拿编出来的数字拦请求——"没有证据，就不定罪"（与 `cost_factor` 的 `missing_default` 同一原则）。

### 2.4 token 估算（TPM/TPD）

token 数取两档，优先级同上：

1. 上游响应里带的 usage（有就用实测）；
2. 本地估算（沿用 `analytics.py` 汇总里已有的"本机观测到的请求和上游返回 Token 统计估算"口径）。

TPM/TPD 的值**永远标注 estimated**，展示层（`quota_view.py`）必须透传这一标注，绝不写成账单口径。估算方法本身是 T2 的实现细节，T1 只定一条：估算只许保守（宁可高估已用，不许低估），且估算规则要写进文档、能复核。

### 2.5 丢计数时宁可保守（安全不变量）

PRD 风险项写死为一条规则，分两种"没证据"，处理相反，不要混淆：

- **上限未知**（三档来源全无）：不守门，只计数。不知道天花板在哪，拦就是编数字。
- **上限已知、已用未知**（窗口数据丢了/损坏了/读不出来）：**按无额度处理**——该键在受影响窗口排干之前视为已耗尽，守门关闭，原因记 `quota_counter_lost`。知道天花板、不知道自己在哪，假设最坏情况。

第二条是本 PRD 的安全底线：丢计数绝不能变成超发。`quota_view.py` 的 band 里要能看到这一状态（T2 加 `band="unknown"` 之外的显式原因字段，不改现有五档枚举——原因走现有 `event_classification`-like 的附加字段，不发明新 band 值）。

### 2.6 reset_at 只是提示，不是复位

`QuotaObservation` 里的 `reset_at`/`retry_at` 是上游给的"下次恢复时间"提示。滑动窗口**不复位**——窗口是滑出去的，不是清零的。`reset_at` 只做两件事：展示层给出"最早可重试"提示；守门在窗口排干后自然放行。T2 不得实现"到 reset_at 就清零计数器"的逻辑（那会把窗口内真实已用的请求一笔勾销）。

### 2.7 存储与恢复

- 新表 `quota_windows`，放在同一个 `usage.db` 里（沿用 `AnalyticsStore` 的 0600 权限、WAL、30 天保留期约定）：`(key TEXT, window TEXT, bucket_ts INTEGER, requests INTEGER, tokens_est INTEGER, PRIMARY KEY(key, window, bucket_ts))`，索引 `(key, window)`。过期桶随 `AnalyticsStore.purge` 一起清（分钟桶超 2 小时、日桶超 48 小时即死数据）。
- 热路径是**内存环**：`QuotaLedger` 在内存里持每个键的桶数组，守门只读内存（微秒级）；SQLite 是持久镜像，落定时写、周期检查点、重启时恢复。T2 验收：重启后计数不归零（PRD 表格已定）。
- 恢复时最多丢"检查点之后、落定之前"的一小段计数；丢的部分按 §2.5 第二条处理（保守关闭），不静默放行。

## §3 在途租约

### 3.1 机制

每次派发（executor 真正要把请求发往上游之前）先向 `QuotaLedger` **领一个租约**，落定（成功/失败/超时/客户端中途取消，任何路径）时**释放**。租约是"进行中也算数"的唯一实现：

```
放行条件（每维都要过）：recorded + in_flight < limit
```

- `recorded`：窗口内已落定的计数；`in_flight`：活着的租约占用的量；`limit`：§2.3 的上限。
- 用严格小于：到上限就停，不许"正好等于上限再发一个"。
- TPM 的租约在领的时候就要占 token：提示词 token 已知全额占；补全 token 未知，占一个**补全预留**（默认 512，`routing.policy` 可调，决策点 D1）；落定时按实际 usage 多退少补（只退不追——实际超了预留不补扣，记一次 `tokens_under_reserved` 观测供以后调预留）。

### 3.2 释放幂等与泄漏清理

- 释放幂等：重复释放是空操作（debug 级日志，不报错、不重复扣减）。executor 必须在 `finally` 里释放——任何提前返回、异常、取消路径都不得漏。
- 泄漏清理：租约最大存活期 300 秒（照 `failover.TimeoutPolicy.total` 的总预算）；清理器每 60 秒扫一轮，并对每个键在下一次领租约时懒清理。超期租约按"请求已死"处理：释放占用，但记一条 `lease_swept` 观测（供 T5 复核泄漏率）。
- 租约只放内存，不落盘。进程重启即丢租约，这是**安全**的：进程死了，它发出的请求连接也断了，不存在"重启后上游还在跑、本地却忘了占位"的活请求。

### 3.3 并行不再集体越线（论证，T3 要测出来）

今天的集体越线是因为守门读的是**上一次落定的快照**，N 个并行请求看到的是同一个数。租约把"在途"变成了"已占"：第 1 个请求领走 1 个名额后，第 2 个请求读到的 `in_flight` 已经是 1。N 个并行请求对上限 K 的派发，上限是 K 次——不是"至多 K 次落定"，是"至多 K 次发出"。T3 的验收测试必须用假时钟 + 假上游复现这个场景（N=50 并行、上限 K=10，发出数 ≤10），而不是只测串行。

### 3.4 谁是租约的唯一主人

executor 是唯一领租约、唯一释放租约的地方（single writer）。planner 只**读**计数（§4）。不许出现 planner 和 executor 各持一份计数的双写——双写必然漂移，漂移必然超发。

## §4 平台共享池建模

### 4.1 池映射表是数据，不是代码

池映射是一张数据表（默认随仓库走一份，可热修、可覆盖，reload 不重启，沿用 `routing.policy` 的重载路径），格式：

```yaml
pools:
  - pool_id: openrouter::free
    platform: openrouter
    scope: models_suffix_free   # 该平台下 :free 后缀模型共用一池
    evidence: freellmapi 额度文档（借鉴源口径）
  - pool_id: google::project
    platform: google-ai-studio
    scope: per_slot              # 按项目计量；本仓库一 key ≈ 一项目，故按槽分池
    evidence: freellmapi 额度文档
```

初始行只写**有证据**的池（上面两行 + groq 按账号、NVIDIA 共用额度池，证据均引 freellmapi 额度文档）；其余 6 家提供方在证据补齐前一律标 `scope: unknown`，即**不假设共享、按模型计量**。映射错的代价是系统性误判，所以宁可漏标、不可错标；映射表每行必须带 `evidence` 字段，没证据的行不许进表。

### 4.2 池守门

池有自己独立的四维计数（键 `pool:{pool_id}:{window}`），与 §2 同一套窗口实现。一次派发要过**两道门**：

1. （平台，模型，槽）窗口门；
2. 所属池窗口门（若该模型属于某池）。

两道门都过才放行；任一道不过，拒绝原因写清是哪一道（`quota_window_exhausted` 带 `scope=model|pool` 与 `pool_id`）。池计数统计池内所有模型的派发——池内 A 模型烧掉的额度，B 模型看得见。

### 4.3 池与 BYOS

BYOS 订阅网关（`byos/base.py` 的 `subscription_gateway`）**不进免费池**。订阅的计量单位是订阅本身，不是免费池；池映射只覆盖免费档计量。BYOS 密钥的额度仍由 §2 的（平台，模型，槽）窗口计量（它也是上游限流），但不参与任何池计数。

## §5 与选路的接线口径

### 5.1 守门放在哪一步

在 `RoutePlanner.plan` 里，**现有 resilience 排除之后、打分之前**加一道 quota 窗口门：

```
plan 流程（新增一步标 *）：
  1. 别名/显式解析
  2. 工具调用、byos_disabled、auto/free 证据过滤
  3. resilience 排除（excluded_by_cost：全部槽被拦 → 剔除）
  4. * quota 窗口门：窗口计数 + 在途租约不过 → 剔除，原因 quota_window_exhausted
  5. 三维打分（质量 0.5 / 成本 0.3 / 延迟 0.2）
```

理由：放在打分前，被打分的集合就是"可派发"的集合，分数之间可比；剔除走现有的 `rejected` 通道（`{"model": ..., "reason": ...}`），**不发明新字段名**。权重体系不动——窗口门是"能不能发"，不是第四维。

### 5.2 成本维怎么用本地计数

`cost_factor` 的输入仍是 `signals["quota"]`（实时剩余/上限比），来源优先级：

1. 上游响应头实测比（现有行为，不变）；
2. 本地计数推导比 `used/limit`——**只在上限有证据（§2.3 前两档）时才推导**，`quota_source` 标记为 `local_counter`，展示层可见。

本地计数是**门**，不是**分**：推导比只让成本维在上游沉默时也能工作，不改变 `cost_factor` 的降权规则（低于 0.10 降权不截断、无数据 0.5 默认分），不改变权重。

### 5.3 与 prefer_subscribed 的次序

`prefer_subscribed`（PRD-173/T3）的订阅桶排序发生在 quota 窗口门**之前**：订阅候选先排到前面，再统一过 quota 门。订阅身份不豁免 quota——订阅是"愿意付费"，quota 是"上游让不让发"，两回事。订阅候选被 quota 门拦下时，照常落到下一个候选，不因为是订阅的就放行。

### 5.4 planner 的门是建议，executor 的租约是硬门

planner 的窗口门读的是内存快照，读与发之间有竞态（两个 planner 并行、或 planner 读完 executor 才发）。所以设计是两层：

- planner 门：便宜的建议，避免把注定发不出去的候选推进打分与执行；
- executor 租约：唯一的硬门，领不到租约就不发。

两层不一致时以 executor 为准；planner 误判（放了 executor 拦下的）记一条 `quota_gate_drift` 观测，供 T5 复核两层漂移率。漂移率长期非零说明 planner 快照太旧，T5 要给出结论（收紧快照频率或接受漂移）。

## §6 边界（写死）

### 6.1 与 PRD-173 BYOS 额度

| 维度 | PRD-173（BYOS） | 本 PRD（467） |
|---|---|---|
| 管什么 | **接入**：哪些密钥存在、订阅状态、`prefer_subscribed` 排序 | **计量**：窗口内花了多少、还剩多少、能不能发 |
| 真相源 | 密钥清单 = 注册表 / BYOS 配置 | 上限值 = 上游响应头 > 已核实文档值 > 签名目录；已用量 = 467 计数器 |
| 不碰对方 | 173 不计数（不持有窗口、不领租约） | 467 不注册密钥、不改订阅状态、不改 `byos.enabled` |
| 交集 | BYOS 密钥的额度仍由 467 计量（上游限流与订阅与否无关）；BYOS 网关不进免费池（§4.3） | |

### 6.2 与 PRD-096/T2 quota 感知路由

096/T2 是**消费者**，467 是**生产者**：

- 096 拥有观测管线：`quota.py` 的解析、`ResilienceManager` 的状态、`quota_view.py` 的展示、`cost_factor` 的接线。467 不改其中任何一个的现有行为。
- 467 拥有计数管线：窗口、租约、池。467 向 096 的 `signals` 字典里**只加一个值**：`signals["quota"]` 的推导比（上限有证据时）与 `quota_source="local_counter"`；另加一个拒绝原因 `quota_window_exhausted`（走现有 `rejected` 通道）。
- 信号的形状（`QuotaObservation` 字段）由 096 定；若 096 改形状，467 跟着改——消费者拥有契约。

### 6.3 与 PRD-468 冷却阶梯

468 管"撞线之后怎么办"（冷却阶梯、探测恢复），467 管"知道快撞线"（计数）与"防止撞线"（守门）。467 **永不设置冷却**；468 **永不计数**。接口：467 在窗口门拦下一次派发时发一条 `quota_gate_hit` 事件（提供方/模型/槽/池/维度），468 可以把它当提示消费——但注意：**门拦下是" prevented 429"，不是失败**，它不得计入任何失败计数、不得触发冷却、不得拉长任何阶梯。把"没撞上"记成"撞上了"，是本设计明确禁止的因果倒置。

### 6.4 与 PRD-469 Retry-After 解析

469 拥有"从响应头/正文里解析声明的等待时间"；467 只消费 `QuotaObservation.retry_at`（已存在）当作窗口提示。467 **自己不解析 Retry-After**。

### 6.5 与 PRD-201 可观测看板

quota 窗口/租约/池是**可观测状态**，不是 UI。T2 必须提供一个只读快照接口 `QuotaLedger.snapshot()`：每键的四维（已用/上限/还剩/下次恢复提示）与池归属；只含槽序号，不含密钥原文。看板怎么画是 201 的事；467 只保证快照存在且便宜（读内存，不扫 SQLite）。

### 6.6 与 PRD-466 签名目录

466 的目录若含 rpm/rpd/tpm/tpd，是 §2.3 的第 3 档上限来源。467 **不拉目录、不验签名**——目录的获取与验证全归 466；467 只读 466 落到本地的上限值，并沿用 466 的版本底线（旧目录不回滚新上限）。

## §7 数据结构与存储

- 新模块 `quota_windows.py`，类 `QuotaLedger`：内存桶数组（热路径）+ SQLite 持久镜像（`quota_windows` 表，§2.7）。不扩展 `quota.py`（它是解析器）、不扩展 `resilience.py`（它是失败状态机）——计数是第三种状态，单立模块。
- 并发：单进程，`QuotaLedger` 内部一把 `threading.Lock`，每次操作持锁极短（桶求和 O（桶数））；executor 单写、planner 只读快照。**不引入进程间锁**：本仓库是单进程网关，多进程部署不在本 PRD 范围内（若将来多进程，计数需另立集中存储，T5 报告里写为已知局限）。
- 隐私：键里只有槽序号；日志行过既有 `SENSITIVE_PATTERN` 脱敏（沿用 `failover_decisions` 的做法）；token 数只记量，不记内容。
- 失败永不中断主流程（沿用 analytics "failures never interrupt" 的惯例）：计数器写失败记 warning、降级为"上限已知按 §2.5 保守关闭"，绝不让一次 SQLite 报错打断一次用户请求；读失败同理。

## §8 T2–T5 契约

### T2 滑动窗口计数（#2256）

- 输入：`QuotaObservation` 的上限（§2.3 三档）+ executor 的派发/落定事件。
- 输出：`QuotaLedger` + `quota_windows` 表；四维计数可用；重启恢复。
- 验收：计数与真实请求一致（假时钟单测）；窗口边界行为有测试（跨分钟/跨日边界）；重启后计数不归零；丢计数时保守关闭（§2.5 的测试用例必须存在）；上限无证据时只计数不守门。

### T3 在途租约（#2257）

- 输入：T2 的 `QuotaLedger`。
- 输出：`acquire` / `release` / `sweep`；executor 在 `finally` 里释放。
- 验收：N=50 并行、上限 K=10 的场景发出数 ≤10（假时钟 + 假上游）；租约泄漏可自愈（超期扫掉）；释放幂等（两次释放只扣一次）；重启丢租约是安全的（§3.2 的论证写进测试注释）。

### T4 平台共享池建模（#2258）

- 输入：T3 的租约 + 池映射表。
- 输出：池窗口门 + 池映射表（数据文件，可热修、可覆盖）。
- 验收：共享池场景（OpenRouter `:free` 两模型共用一池）不再误判剩余额度；池映射表可扩展（加一行无需改代码）；无证据的平台不进池（默认按模型计量）。

### T5 验收试运行（#2259）

- 输入：T2–T4 全部落地。
- 输出：验收记录（并行压测：N 并行 vs 各档上限；429 率对比——上线前后同一批流量、同一批提供方；`quota_gate_drift` 漂移率；`lease_swept` 泄漏率）。
- 验收标准：记录完整、结论可复核；另附"上限溯源审计"：系统里每一个生效中的上限，必须能追到响应头/已核实文档/签名目录三档之一，**无来源的上限视为缺陷**；多进程部署的已知局限写入报告。

## §9 决策点（待评审拍板）

- **D1 补全预留默认值**：TPM 租约的补全预留默认 512 token（T1 建议值，`routing.policy` 可调）。调大更保守（少超发、多误拦），调小反之。T2 可在结构不变下校准。
- **D2 池映射初始证据表**：T1 只敢写 freellmapi 文档里明确提到的四行（OpenRouter `:free`、Google 按项目、Groq 按账号、NVIDIA 共用额度池）；其余 6 家提供方的池行为由 T2 逐家核实证据后填表，**无证据不进表**。
- **D3 租约清理节奏**：清理器每 60 秒一轮、租约最大存活 300 秒（照 `TimeoutPolicy.total`）。T3 可在结构不变下校准。
- **D4 派发侧的 token 估算器**：沿用 analytics 已有的估算口径，还是为 TPM 单立一个估算器——T2 定，T1 要求：只能二选一，不许两套估算并存（两套必然漂移）。

## §10 风险

- 窗口数据丢了 → §2.5 保守关闭，不超发。
- 共享池映射错 → 映射表是数据不是代码，可热修；错标的代价是系统性误判，所以 §4.1 宁可漏标、不可错标。
- TPM 是估算 → 永远标注 estimated；估算只许保守；展示层透传标注。
- 租约泄漏 → 300 秒上限 + 60 秒清理 + 懒清理三重兜底；泄漏率进 T5 验收。
- planner 与 executor 两层漂移 → 以 executor 为准，漂移率进 T5 验收。

## §11 红线

- 只借鉴思路，不复用代码（freellmapi MIT，TS vs Python；出处见文首）。
- 不改 BYOS 接入层；不做额度预测；不改三维权重；不发明上限数字（上限三档来源之外的值一律不许当上限）。
- 文档与示例不得出现真实内部主机名、IP、账号或密钥，一律用占位符；本文示例数字均为"假设"，不是任何提供方的真实额度。
