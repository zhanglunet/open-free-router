# 后端监督台设计草稿（PRD-447/T1）

> 来源：trend issue [#2155](https://github.com/zhanglunet/trend/issues/2155)（[PRD-447/T1] 后端监督台设计）；PRD 全文：`zhanglunet/trend` 仓库 `adopted/PRD-447-ofr-backend-supervision-bench.md`。
> 状态：设计草稿（T1），只开 PR 不合并，等设计评审。
> 范围：本稿只写设计、接口、数据结构与验收标准，不写实现代码，不改本仓现有代码。

## 1. 问题与目标

路由/配额 agent 给出换路建议时，人今天只在换路批准收件箱里看到成品：建议为什么换路、按什么配额算的、备选路为什么被否，全都不可见。可疑建议要等到批准那一刻才被发现，改建议的来回也没有落账。

后端监督台的目标：每一次换路建议先过监督台再进下游。建议自带调度过程，人在台上随手批注、裁决，一键把反馈发回 agent，agent 改完再回来；未点头的建议不进换路批准收件箱；批注与反馈全程留痕。

## 2. 设计要点

### 2.1 监督对象：一条换路建议

一条换路建议是监督台上的一行记录，包含：

- 建议标识：建议 ID、产生时间、发起的 agent 与任务标识。
- 建议内容：拟切换的路由（从哪条路到哪条路）、配额变化、生效窗口。
- 调度过程：agent 做决定时依次走过的推理步骤与中间结论（例如候选路评估、配额测算、否决原因），每一步带时间戳与输入摘要。
- 建议状态：见 2.3 的状态机。

调度过程是只读呈现：监督台展示过程，不重算、不改写 agent 的结论。

### 2.2 数据模型（三件套落账）

监督台落账三类记录，缺一不可：

1. **进度记录**：建议从出炉到裁决的每一步进展（出炉、被查看、被批注、被发回、被改回、被点头/被否决），每条带时间与操作人。
2. **批注记录**：人针对建议或其某一步推理留下的批注（文本、锚定的推理步骤、批注时间、批注人）。批注只附加，不覆盖建议原文。
3. **发回反馈记录**：人一点“发回”时产生的反馈单（反馈类型：换路 / 保路 / 补说明；反馈正文；关联的批注；发回时间）。agent 改完回来的新版本挂在同一条建议下，与旧版本并列可查，版本之间可逐项对照。

三类记录统一用建议 ID 串联；删除建议时三类记录一并归档，不单独抹除。

### 2.3 状态机与关口

建议状态流转：

```
出炉（draft）→ 待审（in-review）→ 已点头（approved）→ 进入换路批准收件箱
                 ↓ 发回（sent-back）→ agent 改完 → 回到待审（in-review）
                 ↓ 否决（rejected）→ 归档，不进下游
```

关口规则（硬性）：

- 只有 `approved` 状态的建议可以进入换路批准收件箱；换路批准收件箱只审人点头过的建议。
- `sent-back` 的建议在 agent 改完回来之前不得进入收件箱；改回来的新版本重新走待审流程，不继承上一轮的点头。
- 否决的建议不进收件箱，只留档备查。

### 2.4 监督接入点

agent 在三个时刻向监督台交数：

1. **建议出炉时**：提交建议内容 + 完整调度过程，状态为待审。
2. **agent 改完回来时**：提交新版本 + 本轮改了什么（对照上一轮的差异摘要），状态回到待审。
3. **状态变化时**：人的每次批注、裁决、发回都实时记入进度记录。

接入方式设计为“建议事件 + 查询接口”：agent 发事件上报，监督台提供按建议、按状态、按时间查询的只读接口；监督台不直接调用 agent 内部函数。

### 2.5 批注 / 裁决 / 一键发回回路

- **批注**：人在建议详情页对任意推理步骤或整条建议写批注；批注即时保存并对同一条建议的所有查看者可见。
- **裁决**：人在建议上做三选一裁决：点头 / 发回 / 否决。裁决必须带理由（点头可留空，默认“同意建议”；发回与否决必须写理由）。
- **一键发回**：点“发回”后，批注与反馈单自动打包成一条反馈消息发回 agent；agent 侧收到的是结构化反馈（类型 + 正文 + 关联批注），不是自由文本转发。

### 2.6 呈现：监督台一屏

一屏三区：左列是待审建议清单（按出炉时间倒序，标出每条的状态与等待时长）；中区是当前建议的详情（建议内容 + 调度过程步骤）；右区是批注与反馈时间线。操作集中在中区底部：批注框、点头、发回、否决四个动作。

### 2.7 与既有模块的划界

- **不管配置评审（PRD-424）**：本台不管配置评审过没有，只管建议出炉的全程人看没看、批没批、agent 改没改。
- **不管异常真假（PRD-378）**：本台不验异常真假，只管监督流程本身。
- **不管待办收发（PRD-364）**：本台不管收件箱的待办收发，只管未点头的建议不进换路批准收件箱。
- **不是协同会话**：人只批注和裁决，不下场改建议内容；改建议是 agent 的事。
- **不是事后审计链**：本台是事中监督 + 反馈回 agent，不是事后留痕；留痕是监督过程的副产品。

## 3. 接口草案

| 接口 | 方向 | 输入 | 输出 |
|---|---|---|---|
| 上报建议出炉 | agent → 监督台 | 建议内容 + 调度过程 | 建议 ID、初始状态 |
| 上报改回版本 | agent → 监督台 | 建议 ID + 新版本 + 差异摘要 | 新版本号、状态回到待审 |
| 提交批注 | 人 → 监督台 | 建议 ID + 锚定步骤 + 批注文本 | 批注 ID、时间戳 |
| 裁决 | 人 → 监督台 | 建议 ID + 裁决（点头/发回/否决）+ 理由 | 新状态 |
| 一键发回 | 人 → agent（经监督台） | 建议 ID + 反馈单 | 反馈已送达回执 |
| 查询建议清单 | 监督台 → 人 | 状态/时间过滤 | 建议清单 |
| 查询建议详情 | 监督台 → 人 | 建议 ID | 建议 + 过程 + 批注 + 反馈时间线 |

所有接口只传业务字段，不传真实内部主机名、IP、账号或密钥；示例一律用占位符。

## 4. 验收标准

1. 一条换路建议从出炉到点头的全程（进度、批注、发回反馈）都能在监督台上查到，缺一类记录即不通过。
2. 未点头的建议无法进入换路批准收件箱（以关口断言覆盖：待审、发回中、已否决三种状态各至少一条反例）。
3. 发回后 agent 改回的新版本重新待审，不继承上一轮点头。
4. 批注锚定到具体推理步骤可查；反馈单包含类型、正文与关联批注。
5. 设计评审通过（T1 本身的验收标准）。

## 5. 红线

- **学习网关只出推荐，不自动执行。** 监督台本身不触发任何路由切换；换路建议无论点头与否，都不由监督台执行，只由下游既有流程按既有审批执行。
- **未点头的换路建议不进换路批准收件箱。** 这是本设计的硬关口，不设例外通道、不设绕过开关。
- **人只批注和裁决，不下场改建议。** 监督台不提供直接编辑建议内容的入口。
- **文档与示例中不得出现真实内部主机名、IP、账号或密钥，一律用占位符。**
- **实现类 PR 只开不合并，等用户 review。** 本稿是设计草稿，后续 T2–T5 的实现 PR 同样只开不合并。
