## 1. 背景：本轮做了什么，为什么需要它

v0.3.0 之前，站点从 4 个页面长到 16 个，但**没有任何自动化质量门禁**：
`npm run test:web` 只覆盖 worker 的 3 个纯函数（18 个断言），页面本身
从未被机器检查过。结果是一批只在真实浏览器里才暴露的缺陷长期存在于
生产环境。

本轮引入全站审计工具 `npm run test:site` 后，一次扫描发现 **58 个问题
（1 critical / 42 major / 15 minor）**，全部修复，现在归零。

### 1.1 被漏掉最久、影响最直接的三类缺陷

| 缺陷 | 用户实际看到什么 | 为什么测试没抓到 |
|---|---|---|
| `style-src 'self'` 拦截了 `style="--meter/--score"` 属性 | 首页四条能力条、模型雷达整列「功能指数」条**全部渲染成 0 宽度** | 本地直接打开 HTML 文件不触发 CSP；只有真实浏览器 + 真实响应头才复现 |
| `frame-ancestors` 只写在 `<meta>` 里 | 点击劫持防护**从未生效**，且 15 个页面每次访问都往控制台打错误 | 浏览器静默忽略该指令，页面看起来完全正常 |
| `--dim: #587087` 对比度 3.0–3.7:1 | 12 个页面的小字说明、图例、时间戳**低于 WCAG AA 正文门槛 4.5:1** | 深色主题下肉眼「看得见」，但低视力用户和强光环境下读不了 |

### 1.2 结论

站点已经是产品的主要入口（安装指南、模型雷达、实时状态都在这里），
它需要和 Python 后端同等的测试待遇。**质量不能靠人工巡检维持** —— 这是
本 PRD 后续所有优先级排序的第一依据。

## 2. 已交付：质量基线（P0，本轮完成）

### 2.1 全站审计工具 `npm run test:site`

两层结构，静态层零依赖、永远可跑；浏览器层缺少 Chromium 时优雅跳过
而不是失败，保证裸检出和无浏览器的 CI 镜像里仍然有用。

**静态层**（`web-tests/site-audit.mjs`，无第三方依赖）
- 死链与资源缺失：解析全部 `href`/`src`，逐个核对磁盘（含 `?v=` 查询串剥离）
- 锚点完整性：页内与跨页 `#anchor` 必须在目标页面存在对应 `id`
- HTML 结构：唯一可见 `h1`、重复 `id`、`lang`、标题唯一性与长度
- 元数据：`title` / `description` / `viewport` / CSP meta
- CSP 合规：内联 `style=` 属性、`<style>` 块、内联 `<script>`
- 图片 `alt`、外链 `rel=noopener`
- `sitemap.xml` ↔ 真实页面双向一致；`robots.txt` 前缀覆盖判定

**浏览器层**（playwright-core + axe-core，可选依赖）
- 控制台报错、未捕获异常、失败请求、**运行时 CSP 违规**
- axe-core WCAG 2.1 A/AA 全量规则
- 三档视口（375 / 768 / 1440）横向溢出检测，自动定位越界元素
- 网络空闲后仍停在加载态的页面（门控页按表单存在自动豁免）
- 点击目标尺寸，按 WCAG 2.5.8 的 24×24px 门槛，并实现两条法定豁免：
  行内链接豁免、以及页面通过 `data-target-size="essential"` 显式声明的
  「呈现方式必要」豁免（散点图数据点属此类，页面已提供等价数据表格）
- 404 路径返回码与内容

退出码在存在 critical/major 时非 0，可直接作为部署门禁。

### 2.3 第二轮：对抗性深度审计（24 项）

机械审计能证明「链接不死、对比度达标、无 CSP 违规」，但证明不了
**页面说的话是不是真的**。第二轮用 6 个维度的独立审计 + 每条结论单独
对抗性验证，补上了这一层：

| 维度 | 代表性发现 |
|---|---|
| 内容准确性 | 首页宣传「Gemini 3.6 Flash · 1M context」「Nemotron 3 Ultra · 256K」——注册表里没有这两个模型，55 个模型**全部**是 131K；指南图示里 5 个模型 ID 复制过去直接 404；npm 指南让用户用 `--version` 验证安装，而该参数从未注册（退出码 2） |
| 数据契约 | `devlog.json` 存 `{label, href}`，`logs.js` 读 `link.url` → **13 条开发日志链接全部指向 `#`**；模型雷达离线兜底声称候选为 0，而 129 KB 的候选快照就部署在旁边 |
| Worker 韧性 | `/api/catalog` 把 discovery 放进同一个 `Promise.all`，models.dev 一挂整个模型雷达 503 |
| 无障碍语义 | 状态徽章与散点图**仅用颜色**表达可用性；`aria-live` 每次刷新重播整块看板；`/guide/npm/` 同时播报两个「当前页」；移动端导航面板无对话框语义、无焦点管理；地图标记在未悬停时无名称 |
| 视觉与布局 | 粘性顶栏遮挡 6 个锚点目标 |

最终确认 42 项（19 major / 23 minor），全部修复。其中一项值得单独记录：
**上一轮加的安全响应头是死代码**——`wrangler.jsonc` 的
`run_worker_first: ["/api/*"]` 决定了页面与静态资源请求由 Cloudflare 的
Asset Worker 直接响应，根本不进入 `fetch` 处理器。改用平台原生的
`site/_headers` 后，`wrangler dev` 实测五个头全部下发。

**结论**：两类审计互补且都必要——机械审计防回归，深度审计防失真，而且
**深度审计能发现机械审计自己修复中的错误**。后者成本高（本轮 61 个 agent），
适合按版本节奏跑，而不是每次提交。

另有一条反向验证：本轮补社交元数据时正则漏了闭合的 `>`，破坏了 13 个页面的
标签结构并导致 CSP 被浏览器丢弃——**是机械审计的浏览器层当场抓住的**。
已把「标签未闭合」「CSP 不在 head 内」补进静态层，让这类编辑快速失败。

## 3. 下一阶段需求

优先级依据：**能否防止已修复的问题重新出现** > **用户可感知价值** > **扩展面**。

### P0-1 CI 流水线 ✅ 已实现

**问题**：仓库至今没有 `.github/workflows/`。280 个 Python 测试、18 个 web
测试、全站审计**全部依赖人工在本地执行**。本轮修复的 58 个问题里，至少
CSP、对比度、死链三类会随任何一次页面改动悄悄回归。

**需求**
1. `ci.yml`：push 与 PR 触发，矩阵跑 Python 3.11/3.12 的 `pytest`、
   `npm run test:web`、`npm run test:npm`、`npm run build`。
2. `site.yml`：安装 Chromium 后跑 `npm run test:site`，critical/major 阻断合并。
3. 缓存 pip 与 npm 依赖，目标单次 < 5 分钟。
4. 失败时把审计 JSON 作为 artifact 上传，便于定位。

**验收**：新建一个故意引入内联 `style=` 或低对比度颜色的 PR，CI 必须红。

**补充**：内容准确性检查（页面宣称的模型 ID / 数量 / CLI 参数是否真实存在）
应做成构建期断言而非依赖人工或 LLM 审计——本轮发现的 4 类失真都可以用
「拿页面里的标识符去注册表和 argparse 里查」这一条规则机械捕获。

### P0-2 构建期资源指纹 ✅ 已实现

**问题**：27 个前端资源里只有 6 个带 `?v=20260803b` 手工版本号，其余 21 个
（**包括本轮刚改过的 `styles.css`**）没有任何缓存失效标记。手工维护版本号
必然遗漏——现状本身就是证据。

**需求**
1. `scripts/build-site.mjs` 按文件内容哈希重写引用：
   `/styles.css` → `/styles.<hash8>.css`，产物落到 `web/`，`site/` 保持干净。
2. 带哈希的资源下发 `Cache-Control: public, max-age=31536000, immutable`；
   HTML 保持 `must-revalidate`。
3. 移除所有手工 `?v=` 版本号。
4. 审计工具增加检查：`web/` 中任何被 HTML 引用的 CSS/JS 都必须带哈希。

**验收**：改一个字节的 CSS，构建产物文件名必须变化；未改动的资源文件名保持稳定。

### P0-3 公开目录数据新鲜度 ✅ 已实现（M2）

**问题**：`site/data/catalog.json` 的 `generated_at` 停在 `2026-08-01T17:16Z`，
`status_as_of` 停在 `2026-08-01T15:00Z`。Worker 的 `/api/catalog` 会用 KV 里的
实时状态覆盖，但**静态兜底数据已经两天没更新**——一旦 KV 未命中或 API 降级，
访客看到的是过期快照，而页面上标注的时间戳会让他们以为是新鲜数据。

**需求**
1. 构建时校验：`catalog.json` 的 `generated_at` 超过 N 天则构建失败（默认 7 天）。
2. 定时任务把 `export-public-catalog.py` 的产物提交回仓库，或改为构建时生成。
3. 前端对超过阈值的快照显式降级提示（「静态兜底数据，最后更新 X 天前」），
   而不是照常渲染时间戳。

**验收**：把 `generated_at` 改成 30 天前，构建必须失败并给出明确提示。

#### 本轮实现与取舍（2026-08-03）

设计文档 `docs/superpowers/specs/2026-08-03-m2-data-freshness-design.md`，
实施计划 `docs/superpowers/plans/2026-08-03-m2-data-freshness.md`，
过程记录 `docs/superpowers/2026-08-03-m2-process-log.md`。

**范围被证据改写了三次。** 动手前的调查发现：

1. **今天的快照年龄是 1.54 天**——一个只看年龄的 7 天门禁**当天就是绿的**，
   会在什么都没修的情况下宣告通过。真正的缺陷是已发布产物停在
   `schema_version: 1`。所以门禁断言**形状而不只是年龄**。
2. **最严重的「过期数据当作当前数据」不在静态兜底路径，而在 Worker 实时路径。**
   `mergeServerStatus` 让模型证据过 `recent()`（45 分钟）却无条件拷贝 KV 里的
   提供商摘要。喂入不同年龄的快照实测：**从第 46 分钟起**就会渲染出「可用 ·
   已验证 3/3 个模型可用 · 900ms」的提供商卡片，下面挂着三个「候选未验证」的
   模型徽章；3 天与 30 天的提供商载荷**逐字节相同**。
3. **需求 2 按字面实现会让页面更不诚实。** `status.js` 把
   `status_as_of || generated_at` 填进标着「最近检查」的元素，而
   `metadataOnly()` 会置空前者——每日刷新 `generated_at` 会把诚实的
   「最近检查 2 天前」变成「最近检查 0 秒前」，为一次从未发生的检查报 0 秒。

**一条被实测推翻的前提**：`status_as_of` 原本被认为只能由持有 API Key 的维护者
刷新。`worker/index.js` 的 `/api/status` **无鉴权**公开返回 KV 探测快照，
凭据留在 Cloudflare Secrets、探测在服务端完成。因此**两条时钟都能在无凭据的
CI 里刷新**，硬门禁是正当的。

| 需求 | 实现方式 |
|---|---|
| 1 构建期校验 | `scripts/data-freshness.mjs` 纯函数 + `build-site.mjs` 接入；年龄**锚定到 `min(now, HEAD 提交时刻)`**，另加 schema、计数自洽、未来偏移断言 |
| 2 定时刷新 | `data-refresh.yml` **开 PR 而不是直接提交**（默认 `GITHUB_TOKEN` 的 push 不触发 `ci.yml`/`site.yml`，直接提交会是唯一没有检查的变更）；`scripts/refresh-provider-status.mjs` 从 `/api/status` 取回证据并**单调安全**投影 |
| 3 前端显式降级 | `status.js` / `models.js` / `benchmarks.js` 的兜底分支**无条件降级**——该分支本来就知道没有实测，因此**任何前端文件里都不存在年龄常量** |

**取舍与明确不做的**

- **不做 `--allow-stale` 逃生舱**。提交时刻锚定之后，30 天前的提交带 30 天前的
  目录会通过，今天的提交带 30 天前的目录会失败——门禁不再因为与被测提交无关的
  原因触发，逃生舱失去存在理由。git 元数据缺失时回落墙钟，方向更严格，失败安全。
- **`status_as_of` 只打印不阻断构建**。构建按非目标不联网，`ci.yml` 的 node job
  里也没有 Python，硬失败清不掉。改由 `data-refresh.yml` 与
  `deployed-freshness.yml` 执行。
- **构建期门禁保护的是仓库，不是访客**。仓库**没有部署工作流**，部署是人工
  `npm run deploy`。因此新增 `deployed-freshness.yml`——**唯一测量访客实际收到
  什么的检查**。它今天就是红的，因为线上仍是 schema 1，这是准确信号。
- **`site/_headers` 增加 `/data/*.json` 规则**。它没有被指纹化，此前没有任何
  缓存规则，访客可能在崭新部署上拿到比门禁阈值还旧的目录。
- **单调安全投影意味着静态文件永远不会带来坏消息**。实测 `/api/status` 此刻就把
  google-ai-studio 与 openrouter 报成 `unavailable`，原因纯粹是限流我们自己的
  探测；且轮换批次让任何单次快照约一半模型没有证据。宁可少报可用，不可误报故障。
- **三份 `degradeCatalog()` 故意重复不共享**。`build-site.mjs` 先哈希再重写引用，
  且 `_headers` 把 `/*.js` 标为一年 immutable，JS→JS 引用漂移是**硬 404 打死整页**。
  构建断言保证三份都在。
- **逐模型可用性仍是伪造的**（`public_catalog.py` 把提供商结论盖到 55 个模型上）。
  M2 范围外，但路径已知：`/api/status` 带有以 `provider/model` 为键的逐模型证据。
  记入 M3。
- **七个陈旧度常量共存**，`worker/probe.js` 顶部把它们全部点名。统一是 M3。

### P0-4 提供商接入正确性 ✅ 已实现（M2.5，计划外）

这一条**不在原 PRD 里**。它源于 M2 之后的一次调查：为什么 gitee-ai 全部 16 个
模型返回 HTTP 400。追下去发现的是一族更广的缺陷——**页面上关于单个模型的几乎
每一项断言，实际来源都是对它某个兄弟模型的一次探测**。

36 个 agent 的对抗性诊断里，32 条候选断言被证伪 29 条；本节只记录活下来的。

**做了什么**

| 层 | 缺陷 | 实测 |
|---|---|---|
| 探测 | 非 2xx 时先 `cancel()` 响应体，唯一能区分「我们的凭据不对」与「账号没权限」的物证被丢弃 | 现读 ≤512B、脱敏、截断 300 字符 |
| 探测 | 空白 secret 与有效密钥无法区分（`Authorization: Bearer ` 在 gitee 返回 400 而非 401） | `credentialFor` 加 `.trim()` |
| 探测 | 401/402/403/429 与超时说的是**我们**，却与真实故障一样标为「不可用」 | 逐模型「不可用」35 → 18；OpenRouter 整家 9 个模型不再因限流变黑 |
| 探测 | 一次 429 会覆盖五分钟前成功的测量 | 未取得证据的结果不再顶掉有效期内的既有结论 |
| 数据 | `public_catalog.py` 把提供商结论盖到旗下每个模型 | 27「可用」→ 17 有自身证据 / 38 待验证 |
| 前端 | 两个 `flatten()` 用提供商结论与延迟覆盖每一行 | 徽章矛盾 6/55 → 0；延迟单元格 25/55 → 0 |
| 前端 | `speed_tier_zh` 是冻结的提供商推导值 | 生产上 17 个 unavailable 标着「中等/较慢」，2 个 800ms 标着「当前不可用」 |
| 数据 | 提供商 `reason` 的比例与已发布模型数矛盾 | 「已验证 1/3 个模型可用」而 `model_count: 2`；比例改为按已发布模型集重写 |

**移除 Gitee AI**（维护者决定）。诊断结论：400 来自**探测账号没有计费资源**，
一个模型（`kimi-k2-instruct`）已被上游停用。同时移除
`google-ai-studio/gemini-2.5-flash-lite`——上游明确回复「不再向新用户提供」，
而照安装指南注册的访客全是新用户。基线由 11 提供商 / 55 模型变为 10 / 38。

**值得单独记住的一条**：`site/validation/` 早就写着 Gitee AI「不是可用免费渠道 ·
当前账号无可用计费资源」，而默认注册表同时在把它的 16 个模型当免费模型发布。
**证据一直在我们自己的站点上**——不是探测能力不足，是**结论没有回流到注册表**。

**新增的守卫**

- 离线别名守卫：页面与 README 宣传的每个 `prefix/model` 必须能在已发布目录里解析。
  用三次真实历史回归验证（`gq/llama-8b`、`nv/nemotron-ultra`、`or/gpt-oss-20b-free`）。
- 页面计数守卫：页面上写死的提供商 / 模型数必须与已发布目录一致；地图的数字
  从它自己的标记推导。**第一版只覆盖我记得的三种措辞，九处失真里只抓到两处**，
  被评审指出后改为 grep 站点上每一个数字得出名词表，七处逐一还原验证。
- devlog 守卫：`site/**` 变更必须同时改 `site/data/devlog.json`（`site/data/**` 除外，
  否则与定时刷新 PR 互相死锁）。

**留下的已知项**

- `http_400` 仍归为「不可用」。gitee 的案例说明它可能是账号问题，现已按上游消息
  识别；但状态码本身的含义仍然含糊。
- 七个陈旧度常量互不协调（已在 `worker/probe.js` 顶部全部点名，无强制一致性）。
- 指纹排序隐患：`build-site.mjs` 先哈希后重写引用，JS→JS 引用会导致硬 404。
  目前休眠（无跨文件引用），也是三份 `degradeCatalog()` 故意重复的原因。
- `registry.default.yaml` 里没有任何 `free_tier` 证据，而 `/validation/` 在宣称
  免费层已核验——模型雷达「免费证据」列因此全部显示「条件未知」。**与上面
  Gitee 的教训同类：结论没有回流。**

### P1-1 英文站点 ⏸ 暂缓（决定：暂时不做）

**问题**：13 个页面全部 `lang="zh-CN"`，仓库有 `README.en.md` 但站点无英文版。
项目接入的 11 家提供商中 6 家在美国，目标用户有相当比例不读中文。

**需求**
1. `/en/` 路径下提供首页、模型雷达、实时状态、安装指南四个核心页面的英文版。
2. `hreflang` 互链 + `sitemap.xml` 同步收录。
3. 数据驱动页面（雷达/状态）的中文字段（`description_zh`、`recommended_for_zh`
   等）需要英文对应字段，`public_catalog.py` 同步产出。
4. 审计工具的元数据/结构检查自动覆盖新页面（当前已按目录遍历，无需改动）。

**验收**：`npm run test:site` 对英文页面同样 0 critical/major；语言切换不丢失当前页面。

### P1-2 视觉回归与截图自动化

### P1-3 性能预算 ⏸ 暂缓（实测后重新定义）

**2026-08-03 重新实测**（HTML + 引用的 CSS/JS，指纹化产物，不含图片）：

| 页面 | 当前 | 对照 80 KB 提案 |
|---|---|---|
| `/architecture/` | 71.4 KB | 通过 |
| `/guide/` | 67.3 KB | 通过 |
| `/benchmarks/` | 65.5 KB | 通过 |
| `/models/` | 60.8 KB | 通过 |
| `/validation/` | 59.5 KB | 通过 |
| `/status/` | 56.8 KB | 通过 |
| 其余 10 页 | 1.9–50.8 KB | 通过 |

**这条需求按原样实现会重蹈 M2 的覆辙。** 16 个页面全部在提议的 80 KB 之内，
图片也一样——最重的 `/map/` 只有 112.7 KB，离 500 KB 门槛很远。两条断言
**第一天就是绿的，什么都不会改善**，正如 M2 里「1.54 天的快照通过 7 天门禁」。

实际趋势是页面在**变重**：`/architecture/` 从 68.5 KB 涨到 71.4 KB，原因是本轮
加入的前端逻辑（逐模型证据、降级路径）。预算的价值因此在**防止继续膨胀**，
不在修复今天的问题。

**重新定义后的需求**

1. 预算取**当前实测值 + 10%** 作为每页上限并写死在审计工具里，超出即 major；
   而不是取一个所有页面都够不着的整数。这样它明天就能拦住回归。
2. 拆分 `styles.css`（23.1 KB，被全部 16 个页面加载，其中 hero / orbit /
   live-strip 等为首页专属）。**这是本条里唯一有实质收益的一项**，约 8–10 KB/页。
3. ~~大图检查~~ —— **划掉**。上一轮已把图片从 542 KB 压到 227 KB，现在没有任何
   页面接近阈值；最大单个资源是 `world-dots.svg` 85.4 KB，可接受。
4. `/architecture/` 内联 SVG 外链化 —— **倾向不做**。它的 30.7 KB HTML 里大部分
   是内联 SVG，外链后可缓存，但多一个请求且首屏出现空白，收益存疑。

**验收**：每页进入按实测基线设定的预算；断言进 CI；`styles.css` 拆分后公共层
不含首页专属规则。

### P1-4 官方 Docker 镜像 ⏸ 暂缓（有前置阻塞项）

**排期时发现的阻塞问题：代理与管理页都只绑定回环地址。**

```
src/open_free_router/proxy.py:825   host: str = "127.0.0.1"
src/open_free_router/ui.py:109      host = "127.0.0.1"
```

在容器里这意味着端口映射出去之后**从外面根本连不上**——镜像做出来是不能用的。
所以 P1-4 的第一步不是写 Dockerfile，而是让绑定地址可配置。

**这个前置改动触及安全边界，需要单独设计与评审**：

- **不能顺手把默认值改成 `0.0.0.0`**，那会让所有本机用户的代理暴露到局域网。
  合理做法是新增 `proxy.host` / `ui.host` 配置项，镜像在自己的配置里设为
  `0.0.0.0`，本机默认保持 `127.0.0.1`。
- 绑定到 `0.0.0.0` 之后，`proxy.token` 从「只有本机能读的文件」变成**唯一防线**，
  需要连带复核 token 强度与 UI 鉴权路径。
- `proxy.py:396` 已有一条注释预见了这种情况（"if this ever ends up reachable
  beyond localhost"），但当时只是防御性措辞，没有对应的配置项。

**前置项解决后的常规步骤**

1. 多阶段构建（builder 装依赖 → slim 运行）；运行期依赖只有 `pyyaml`、
   `requests`、`ruamel.yaml`，全部纯 Python 或有 manylinux wheel。
2. 非 root 用户运行；`HEALTHCHECK` 打 `/health`（端点已存在）；暴露 8337 与 9057。
3. `docker-compose.yml` 挂载 `~/.config/open-free-router`（`registry.yaml` 内含
   API Key，**绝不能进镜像层**）与 `~/.local/share/open-free-router`（`usage.db`）。
4. CI 增加镜像构建与 `docker run … doctor` 冒烟。

**验收**：`docker run` 后 `open-free-router doctor` 在容器内通过；镜像 < 200 MB
（`python:3.12-slim` 基础约 150 MB，加依赖约 170–180 MB，达标但不宽裕；
alpine 更小但 musl 下需重新验证 wheel）。

### 4.1 观察期（2026-08-03 起）

**决定：M3 与 M4 暂不启动，先让站点自己跑一段时间。**

这不是搁置，而是因为**现在缺的是运行数据，不是开发工时**。本轮建成的自动化
每天都会产出证据，观察期结束时会有比现在更好的排期依据：

| 每天自动产出 | 能回答的问题 |
|---|---|
| `data-refresh.yml` 开的刷新 PR | 目录内容多久真正变一次？`status_as_of` 是否稳定前进（即线上探测有没有停摆）？ |
| `deployed-freshness.yml` | 线上产物与仓库的落差有多大？部署节奏是否需要自动化 |
| `/api/status` 的 `upstream_error` | 除 gitee 之外，还有多少「不可用」其实是账号或限流问题 |
| 逐模型证据 | 哪些模型长期「待验证」（说明我们的探测账号覆盖不足），哪些真的在坏 |

**观察期内不做**：英文站、性能预算、Docker、以及 §P0-4 末尾那批已知项。

**观察期内仍会自动发生**：定时刷新 PR（需人工评审合并）、线上新鲜度告警。
两者都不需要开发介入；如果刷新 PR 连续多日只改时间戳，说明目录已经稳定，
那本身就是一条结论。

**建议的复盘触发条件**（满足任一即值得重新排期）：

1. `deployed-freshness.yml` 连续多日红 → 说明部署节奏需要自动化，优先级高于 M3/M4。
2. 刷新 PR 出现 `api` 字段或 `schema_version` 变化 → 上游有实质变动，需人工判断。
3. 某个提供商长期全部「待验证」 → 探测账号或凭据需要处理，与 Gitee 同类。
4. 有人实际反馈需要英文文档或 Docker → 需求从假设变成事实，再排 M3/M4。

M1 是其余所有里程碑的前置：**没有 CI，后面每一项都会重新退化成人工巡检**。

**M1 实测验收（2026-08-03）**

| 验收项 | 结果 |
|---|---|
| 故意引入内联 `style=` | 静态层报 major，退出码 1 |
| 故意把 `--dim` 改回低对比度 | 浏览器层 axe 报 4 处 color-contrast |
| 故意引入死链 | 静态层报 critical，退出码 1 |
| 未指纹资源被 HTML 引用 | 构建期守卫直接抛错 |
| 同样输入重复构建 | 文件名稳定（`styles.b840d91a.css`） |
| 改一个字节 | 文件名变化（`b840d91a` → `3ae071bc`） |
| `wrangler dev` 实测缓存头 | 指纹资源 `max-age=31536000, immutable`；HTML `max-age=0, must-revalidate` |

一处实现细节值得记录：CI 里的审计**不能**用 `npm run test:site -- --json`，
因为 npm 会把自己的横幅写进 stdout 污染 JSON 报告；必须直接调用
`node scripts/audit-site.mjs --json`。同时 workflow 显式断言
`browserSkipped` 为空——否则 Chromium 安装失败会让审计"跳过即通过"。

## 6. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| CI 中 Chromium 安装拖慢流水线 | 合并变慢 | 浏览器层拆成独立 workflow 并缓存浏览器；静态层留在主 CI |
| 资源指纹改动构建产物路径 | Cloudflare 缓存与 KV 键可能受影响 | 先 `deploy --dry-run` 验证，灰度一个页面 |
| 英文站增加双份维护成本 | 内容漂移 | 数据驱动页面共用同一份 JSON，只翻译静态文案；审计工具检查两侧页面集合一致 |
| 视觉回归基线频繁失效 | 噪音淹没真实回归 | 只对关键页面设基线，且不阻断合并 |
